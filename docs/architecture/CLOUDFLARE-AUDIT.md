# Cloudflare transition: source audit

The owner selected a Cloudflare target. The root master records the restoration from its changelog and deviation register; missing original details remain open. This audit records the source before Phase 2. On 13 November 2026 the owner authorized local hardening; its current changes and limits are in [WP2-LOCAL-BOUNDS](../plan/tasks/WP2-LOCAL-BOUNDS.md). This audit does not claim a deployed or production-ready runtime. The root master retains its v2.0 text as superseded history; its full original and prior records are under ../archive/aws-v2/.

## Existing, reusable and incomplete

The React/Vite frontend, shared contracts, pure engine rules, local auth boundary and local room lifecycle exist. Local Phase 1 evidence records 164 core, 76 local and 32 browser cases with 34 zero-violation axe scans. Existing real Clerk ticket-sign-in fixtures remain preserved. The engine calculates transitions, deadlines, bids and settlement but its in-memory history is unbounded; its mutation/clone contract must be preserved and tested when adapted. Existing frontend and engine need no blanket rewrite.

apps/api/src/app.ts uses Hono and verifies Clerk server-side, but directly depends on LocalRoomStore and node:crypto; Workers compatibility and identity verification must be tested, including ticket/authorization paths. apps/api/src/index.ts uses Node HTTP/ws, filesystem locks and periodic sweeps. apps/api/src/room-socket.ts relies on local socket/store lifecycle. These need adapter boundaries and a Worker/DO implementation, not a claim of direct portability.

apps/realtime/src/store.ts uses node:fs, node:crypto and EventEmitter, clones and writes the file-backed database on actions and heartbeat, maintains receipts and broadcasts room state. It is a useful local reference, not a SQLite/DO store; it is single-process only. Existing events, actions, privacy rules, accepted prices, authorization and recovery behavior need parity tests. Reconnect currently receives snapshots/polling; bounded retained-event replay and history pagination are unfinished. Local timers run via periodic setInterval/sweep, not durable alarms. No Workers entry, per-room DO implementation, DO SQLite adapter, hibernation or alarm recovery was found in the inspected paths.

The independent ownership.ts coordinator and its tests model leases, fencing and handover; it is not wired into the running app. It is not needed in the selected per-room DO target as the ownership mechanism. Keep it and the existing infrastructure, scripts and migrations until the new runtime passes and the owner separately approves deletion. Model tests can inform failure scenarios but do not prove Cloudflare correctness.

Superseded by Cloudflare architecture v3.0: infra/ and its service definitions, db/migrations/001_initial.sql, scripts/setup-aws.ps1, scripts/aws-mcp-profile.ps1 and the related platform-specific scripts and tests. They are retained unchanged; their existence in the repository or dependencies is not an instruction to run or deploy them. R2 has not been activated.

## Reversal map for v3.0 drafting

D1/D3-D6/D8-D9/D12 and S1-S6/S9: replace the prior container, externally coordinated room owner, shared live store, polling timers and fan-out with Workers routing, one per-room SQLite DO, alarms and hibernating sockets; use idFromName for deterministic routing, while preserving access checks and avoiding unauthorized initialization. D2/S7: retain Clerk, not original custom authentication. D7/S5: restore hibernation, schema/wake handling; do not automatically restore Turnstile or a room-code cache. S8: security protections need a separately reviewed target. S10: cross-room data needs explicit design; do not substitute an unapproved provider. S11: retain suitable tests/tools. S12: capacity remains unproven. D10-D11: replace platform and delivery responsibilities while preserving the historical decision record. Durable Object memory is ephemeral; authoritative data must be persisted transactionally in SQLite, not assumed safe in memory.

## Risks and gates

High complexity: atomic bid and receipt commits, duplicate alarm/requests, restart-safe single settlement, room identity/privacy, reconnect windows and large histories; global room discovery/index consistency and user deletion/export require separate coordination. Runtime compatibility for Clerk and Node dependencies must be tested locally. Hibernation behavior, alarms, socket traffic, storage and CPU limits require measurement. Free-tier limits can fail requests when exceeded; hibernation reduces idle duration but incoming messages and alarm invocations still count. Review current official pricing and limits during v3.0: https://developers.cloudflare.com/durable-objects/platform/pricing/ and https://developers.cloudflare.com/workers/platform/limits/. Free does not establish 1,000-user capacity. No deployments or costs are authorized.

Pricing reference checked 12 November 2026: the Free DO allowance is 100,000 requests/day and 13,000 GB-seconds/day, with 5 million SQLite rows read/day, 100,000 rows written/day and 5 GB stored across the account. Standard incoming WebSocket messages use the documented 20:1 request billing ratio; outgoing messages and protocol ping frames have different treatment, and auto-responses avoid added duration. Worker request and CPU limits are separate. The current client sends an application heartbeat roughly every two seconds; a hypothetical unchanged 1,000-client hour would generate approximately 1.8 million incoming messages, about 90,000 billable DO requests using the 20:1 ratio, before other requests and without claiming a tested workload. Actual billing, hibernation, CPU and capacity depend on the implementation and must be measured.

The original v1.1/blueprint files were not found by repository filename search; the reversal map uses the v2.0 changelog and deviation register and is therefore not a line-by-line comparison with those original documents.

The agreed implementation sequence is in ../plan/CLOUDFLARE-TRANSITION.md. Detailed decisions for the remaining gaps and a full cost model require further work; R2 remains inactive. Package A was subsequently authorized; package B awaits the owner's next instruction after the Phase 2 report.
