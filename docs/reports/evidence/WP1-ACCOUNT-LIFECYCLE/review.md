# Account lifecycle implementation and verification

The single-process development adapter now supports PATCH /api/me for application display names, DELETE /api/me for a durable deletion request, and signature-verified POST /api/webhooks/clerk. The profile dialog provides name editing and an explicit typed deletion confirmation. Custom names use Unicode compatibility normalization, collapsed whitespace and case-insensitive reservation; provider-name collisions receive a distinct label while ownership always uses the verified subject. Custom names survive provider refreshes. Provider timestamps reject duplicate/older projections.

Every authenticated browser request includes an expected-subject assertion. The server compares it to the verified session and rejects a mismatch before mutation; it never authenticates from that header. Client requests also check identity before sending and after receiving. Profile-list responses have a generation guard so an older response cannot overwrite a successful rename. Signing out clears private profile/room state and stale completions cannot restore it.

Clerk account deletion requires a signed first-factor age under five minutes; absent/old age returns the documented useReverification envelope. The client refreshes its token and uses the SDK reverification UI, then signs out only the original session. A local test identity is explicitly separate from Clerk and has no provider reverification. A voluntary deletion requires closing/ending hosted active rooms first. The API commits a job and immediately revokes local sessions/tickets/socket access; the worker calls Clerk, retries with bounded backoff, and completes cleanup after provider deletion. A provider 404 is idempotent success. Hash tombstones block stale tokens and late profile/webhook resurrection.

Shared results keep team/player IDs, accepted prices, budgets and squads. Deleted participant IDs become non-login pseudonyms. Sole-member rooms are removed. A provider-side deletion of an active host ends the auction through the existing engine and settles an accepted leader once. New identity-bearing events carry optional actor IDs so earlier names and departed participants can be redacted. Legacy identity prose lacks reliable authorship and is conservatively scrubbed; financial bid/sale details remain. Old files/events still load. This is local development behavior, not the distributed user store or production deletion worker.
